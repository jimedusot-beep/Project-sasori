## What each reference changed

- **New Elmo implementation:** [jesserockz/love2learn-elmo](https://github.com/jesserockz/love2learn-elmo/tree/d397a7fb094079f6b1cac5605e95f74d1cb8d4b3), pinned `d397a7fb094079f6b1cac5605e95f74d1cb8d4b3`; [Apache-2.0 license](https://github.com/jesserockz/love2learn-elmo/blob/d397a7fb094079f6b1cac5605e95f74d1cb8d4b3/LICENSE) inspected. Its handshake/query/playback facts were checked against the now-acquired app's managed methods and used in original `desktop/elmo_protocol.py` / `desktop/sasori_elmo.py`, without copying implementation or assets. Its author-reported hardware tests remain distinct from Sasori's fake-radio checks and this owner's unit. [Recovered-source review](../../experiments/001-elmo-l2l/recovered-source.md) records differences and exact method provenance. This is the ninth source receipt shown in the recorder.

- **Elmo:** explicit identity and source requirements, an Elmo analysis manifest, historical RX text observations, and a blocked status-query definition with the precise missing authentication/framing/response evidence. Existing BLE inspection remains functional.
- **Bluefluff:** device-specific interpretation is separated from trace ingestion. A captured frame is not silently treated as a complete application message, and unknown bytes retain an unknown interpretation.
- **MiP:** an original offline software-version query definition and codec demonstrate a real manufacturer-documented TX/RX distinction. The [README example](https://github.com/WowWeeLabs/MiP-BLE-Protocol/blob/6123d0250f9b0bb6513d31eb6fbdc8213b5268a4/README.md) specifies raw request byte 14 and an ASCII-hex response. The synthetic example uses those documented bytes with invented timing; it is not a hardware result. The separately selected [live family adapter](../device-action-validation.md) in `site/lib/mip-controls.js` adds only version/status queries and a timed dim-blue/off chest LED action through the documented channels. Web and native enforce fixed commands; real-unit testing remains outstanding. Motion, sound, UART and firmware operations remain excluded.
- **Hacksby:** acoustic research is connected to existing PCM WAV waveform/spectrum analysis through a dedicated source-card handoff. A Furby acoustic decoder/transmitter is not claimed.
- **PixMob:** before/after observation markers, capture-relative timing, same-action comparisons, and a handoff to existing alternating IR pulse analysis. Neither stateful IR replay nor RF transmission is implemented.
- **PulseView:** a bounded frame timeline, explicit decoder selection, byte-versus-interpretation separation, and same-index byte comparisons. This is not a PulseView port or a bus-capture driver.
- **Pybricks:** a model-specific readiness checklist, known-versus-unknown firmware, and explicit recovery availability. No installer, firmware distribution, or Elmo restoration method is supplied.
- **Home Assistant:** versioned declarative adapter manifests with explicit source IDs, capabilities, command availability, and recovery descriptions. The current registry is built in; importing executable adapters or enabling live actions through manifest flags is not supported.

## Primary workflow references

- [Home Assistant integration manifests](https://contributors.home-assistant.io/core/integrations/manifest/) — discovery metadata and integration boundaries; reviewed as documentation, separately from the core-code license above.
- [Pybricks installation and restoration guide](https://pybricks.com/learn/getting-started/install-pybricks/) — supported-hardware setup/recovery workflow; not an Elmo firmware procedure.
- [PulseView project documentation](https://sigrok.org/wiki/PulseView) — timeline and decoder architecture.
- [Android Bluetooth verification/debugging](https://source.android.com/docs/core/connect/bluetooth/verifying_debugging) — owner-controlled HCI logging; log access varies by platform. Sasori's recorder accepts normalized extracted frames, not raw binary btsnoop/PCAP.

## Evidence and next implementation gate

Use [Protocol recorder](../protocol-recorder.md) to preserve TX/RX, identity, source method, and action markers. A measured selected interval is not automatically an acknowledgment or authentication success. Source claims, imported records, source-reported checksums, and synthetic fixtures do not promote an adapter to hardware-verified.

The next Elmo deliverable needs exact message framing, authentication construction/order, a correlated status request/response, and real unit tests. See [source verification](../../experiments/001-elmo-l2l/source-verification.md). The replacement-controller track remains independent: [adapter contract](../adapter-contract.md).
