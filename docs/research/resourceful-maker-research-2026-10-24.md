# Resourceful making: wider research and concrete transfer decisions

Reviewed October 24, 2026. The user's brief is to make Sasori effective with ordinary owned toys and small devices, using the ingenuity of repair shops, independent developers, low-budget makers and open-hardware communities worldwide. This record expands the earlier protocol/inspiration register. Geography helps us discover work; the acceptance criteria are accessible source, reproducible interfaces, licensing, useful behavior and honest test evidence. We do not infer a developer's income or circumstances from their location.

## Strongest new direction: a pocket IR bridge

The current Sasori TV path requires a computer companion; ordinary phone hardware does not supply an IR transmitter. A small BLE-to-IR bridge could remove the computer/Home Assistant requirement for that transport after initial firmware setup. This is an engineering inference from an existing published implementation, not a current Sasori capability. The upstream project's own [phone app](https://koontzie.github.io/ir-remote/app/) is an external demonstration and requires its matching built hardware.

At pinned commit `34c848831abd6bf9e49e50ea3eed971fb245c729`, we read both the README and `firmware/remote_ble/remote_ble.ino`. The implemented interface is:

| Role      | UUID                                   | Reviewed format                                          |
| --------- | -------------------------------------- | -------------------------------------------------------- |
| Service   | `b457c32b-22b1-425f-8a88-4d6dc37ba4eb` | Explicit selected device                                 |
| Configure | `d997012d-7d2b-47de-ae87-bae14df446ef` | JSON with slot 1–5, NEC/SAMSUNG/SONY, code and bit count |
| Trigger   | `58397514-04a3-4265-9590-9d910c4e99d2` | JSON with slot 1–5                                       |
| Status    | `b8ddfe01-519f-430d-bd4e-aba0dd852e2c` | Short `saved`, `sent`, `pressed` or error notifications  |

The firmware confirms NVS persistence and dispatches to the IR library. Its BLE service is unauthenticated, status messages have no transaction nonce, and the single pending-slot variable can be overwritten by rapid requests. A Sasori integration therefore needs deliberate provisioning, serialized requests, bounded notification matching and visible owner observations; a `sent` message cannot prove a TV responded. The upstream author's automatic identification mode is explicitly unproven. We have not run its firmware, flashed a board, measured an emitter or tested a TV.

Acceptance before adding the transport:

1. Select one exact board/revision, documented emitter and USB power arrangement. Verify pin mapping and emitter operation independently. Avoid assuming a circuit for another board is compatible.
2. Build the reviewed firmware reproducibly and record its hash/version. Decide how owner pairing will be established before offering persistent remote configuration.
3. Implement an original scoped browser adapter: explicit device selection, observed service/properties, five named semantic slots, finite operations, cancellation and foreground teardown. Never transmit merely from discovery, import or reconnect.
4. Import one correctly licensed model-specific remote profile. Validate protocol encoding/bit order offline against known vectors before any physical send. Distinguish a discrete power command from a toggle.
5. Prove one useful action on an owned device, then repeat fresh connections, power cycles, rejection and recovery. Hardware revision and observed response belong in the result.

This candidate reuses a bridge across many supported profiles. It does not create universal authentication, identify every device automatically or unlock unrelated toy firmware.

## Implemented alongside this research

This release's original Elmo control engine now offers a ten-minute foreground control session, up to sixty paced sound requests, twenty reviewed catalog IDs, repeated live touch reactions and multi-action performances up to 32 steps/two minutes. The existing quick-check mode and simple remote retain their short one-sound behavior. Sound pacing is a software policy, not a playback-completion acknowledgment. No device was physically tested, and no upstream firmware or application implementation was copied for these changes.

The [Elmo protocol evidence](../../experiments/001-elmo-l2l/recovered-source.md) remains the source of toy bytes. The wider projects inform architecture, low-cost hardware choices and reproducibility; their bytes do not transfer to Elmo.
